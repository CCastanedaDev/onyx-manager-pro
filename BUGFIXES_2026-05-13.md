## 🔴 Bug 1 — Automatizaciones del INI no funcionaban (Mecas ON/OFF, etc.)

### Síntoma
Al aplicar un perfil de configuración (ej: desactivar sentries, cambiar velocidad del día, etc.) mediante el sistema de automatizaciones o el botón "Aplicar Perfil", el `ServerSettings.ini` **no se modificaba correctamente**. Los cambios parecían guardarse en la UI pero no tenían efecto en el servidor.

### Causa raíz
El problema era de **referencia obsoleta (stale reference)** al `ConfigEditor`.

Al iniciar la aplicación, el orden de inicialización era:

```
1. Se crea self.editor = ConfigEditor(...)      ← sin ruta válida aún
2. Se crea self.scheduler = TaskManager(..., self.editor)  ← guarda ESA referencia
3. Se llama _restaurar_ruta_servidor()          ← crea NUEVO self.editor con ruta correcta
   └─ self.editor = ConfigEditor(..., base_path=ruta_real)
   └─ self.scheduler.editor  ← ¡SIGUE APUNTANDO AL EDITOR VIEJO!
```

El `TaskManager` (scheduler) retenía una referencia al `ConfigEditor` original, que apuntaba a una ruta incorrecta o inexistente. Todas las escrituras al INI desde automatizaciones **fallaban silenciosamente** o escribían al lugar equivocado.

### Fix aplicado

**`src/ui/main_window.py`** — método `_aplicar_ruta_servidor()`:
```python
# ANTES: solo se actualizaba self.editor
self.editor = ConfigEditor(self.log_sistema, base_path=ruta_base)

# DESPUÉS: también se actualiza el editor del scheduler
self.editor = ConfigEditor(self.log_sistema, base_path=ruta_base)
if hasattr(self, 'scheduler'):
    self.scheduler.editor = self.editor  # ← FIX CRÍTICO
```

**`src/logic/file_editor.py`** — método `guardar_configuracion()`:
- Se agregó matching **case-insensitive** para mayor robustez
- Se agrega log con la **ruta exacta del INI** que se está editando (ayuda a debug futuro)
- Se usa un `set` para rastrear claves procesadas (más eficiente)

```python
# ANTES: comparación exacta, case-sensitive
if clave_actual in datos_dict:

# DESPUÉS: busca exacto primero, luego case-insensitive
datos_lower = {k.lower(): k for k in datos_dict.keys()}
if clave_actual in datos_dict:
    clave_real = clave_actual
elif clave_actual.lower() in datos_lower:
    clave_real = datos_lower[clave_actual.lower()]
```

## 🟡 Bug 2 — Botón "Actualizar" fallaba / había que presionar varias veces

### Síntoma
El botón **"Actualizar"** (instalar/actualizar servidor con SteamCMD) a veces no hacía nada, tiraba error, o había que presionarlo varias veces para que funcionara. No había feedback visual mientras se ejecutaba.

### Causa
Cada click en el botón lanzaba un nuevo `threading.Thread` independiente apuntando a `instalar_servidor()`. Si el usuario hacía click múltiples veces, se ejecutaban **varios SteamCMD simultáneamente**, lo que generaba conflictos y errores.

### Fix aplicado

**`src/ui/main_window.py`** — nuevo método `_accion_actualizar_manual()`:

```python
def _accion_actualizar_manual(self):
    if getattr(self, '_update_running', False):
        self.log_sistema("⚠️ Ya hay una actualización en curso. Espera.")
        return
    self._update_running = True
    self.btn_update.configure(state="disabled", text="⏳ Actualizando...")
    # ... lanza el thread y restaura el botón al terminar
```

- El botón se **deshabilita** mientras la actualización está en curso
- Muestra el texto `⏳ Actualizando...` como feedback visual
- Al terminar (éxito o error), el botón se **restaura automáticamente**
- Previene múltiples threads simultáneos con un flag `_update_running`

## 🟡 Bug 3 — Auto-Update automático no funcionaba / tira error

### Síntoma
El switch de **Auto-Update** (revisar actualizaciones cada 15 minutos) a veces tiraba error en la consola o dejaba de funcionar. Si se activaba/desactivaba varias veces, el comportamiento era errático.

### Causas

1. **API inestable:** `api.steamcmd.net` a veces responde con JSON vacío o estructura diferente. El código usaba acceso directo por clave (`data['data'][app_id]['depots']...`) que lanzaba `KeyError` y mataba el thread silenciosamente.

2. **Jobs duplicados:** Al activar el switch varias veces sin desactivarlo correctamente, se acumulaban múltiples jobs en la librería `schedule`, causando que el chequeo se ejecutara múltiples veces al mismo tiempo.

3. **Sin lock de ejecución:** Si el chequeo tardaba más de 15 minutos (ej: al descargar una actualización grande), el siguiente tick del scheduler lanzaba otro chequeo en paralelo.

### Fix aplicado

**`src/logic/steam_handler.py`** — método `chequeo_auto_update()`:

```python
# Lock para evitar ejecuciones simultáneas
if getattr(self, '_auto_update_running', False):
    return
self._auto_update_running = True
try:
    # Usar .get() encadenado — nunca lanza KeyError
    public_build = (
        data.get('data', {})
            .get(self.app_id, {})
            .get('depots', {})
            .get('branches', {})
            .get('public', {})
            .get('buildid')
    )
finally:
    self._auto_update_running = False  # siempre se libera
```

**`src/ui/main_window.py`** — método `toggle_auto_update()`:

```python
# Siempre desactivar antes de activar (evita jobs acumulados)
self.scheduler.desactivar_auto_update()
self.scheduler.activar_auto_update(15)
```

## 🟠 Bug 4 — Contador de jugadores online siempre mostraba `---`

### Síntoma
El panel del Dashboard mostraba permanentemente `Jugadores: ---` incluso con jugadores conectados. La consola se llenaba de mensajes `⚠️ [A2S] Sin respuesta...` cada 2 segundos.

### Causa
El sistema usaba el protocolo **A2S** (Valve Server Query) sobre UDP para consultar jugadores. SCUM frecuentemente **no responde a queries A2S** (firewall, configuración del servidor, o simplemente no lo implementa en todos los puertos). Sin respuesta A2S, el contador quedaba en `---` indefinidamente y la consola se spameaba con warnings.

### Fix aplicado

**Nuevo archivo: `src/logic/log_watcher.py`**

Se creó un nuevo módulo `SCUMLogWatcher` que monitorea `SCUM/Saved/Logs/SCUM.log` en tiempo real (como `tail -f`), detectando eventos de conexión y desconexión:

```
Join:  "LogNet: Join request: ..."   → +1 jugador
Leave: "UChannel::Close..."          → -1 jugador
```

**Integración en `src/ui/main_window.py`:**

- El `SCUMLogWatcher` arranca automáticamente al iniciar la app
- Cuando A2S **falla**, muestra el conteo del log en **amarillo**: `Jugadores: ~3 (log)`
- Cuando A2S **funciona**, muestra en **verde** con dato exacto: `Jugadores: 3/64`
- Los warnings de A2S se **silencian después de las primeras 3 veces** (anti-spam)
- El LogWatcher se **reinicia automáticamente** si la ruta del servidor cambia

### Diferencia visual

| Fuente | Color | Formato |
|--------|-------|---------|
| A2S (exacto) | 🟢 Verde | `Jugadores: 3/64` |
| Log (aproximado) | 🟡 Amarillo | `Jugadores: ~3 (log)` |
| Sin datos | ⚪ Gris | `Jugadores: ---` |

## ✅ Cómo verificar los fixes

### Bug INI (automatizaciones)
1. Crear un perfil con `scum.DisableSentrySpawning = False`
2. Aplicar el perfil
3. Abrir el log de sistema — debe aparecer:
   ```
   [Editor] Ruta INI activa: C:\...\ServerSettings.ini
   -> Modificado: scum.DisableSentrySpawning = False
   >> CONFIGURACIÓN ACTUALIZADA.
   ```
4. Abrir el `ServerSettings.ini` y confirmar que la línea cambió (no se duplicó al final)

### Bug Botón Actualizar
1. Hacer click en "Actualizar"
2. El botón debe deshabilitarse y mostrar `⏳ Actualizando...`
3. Hacer click de nuevo — debe aparecer mensaje en consola "Ya hay una actualización en curso"
4. Al terminar, el botón se restaura solo

### Bug Jugadores
1. Iniciar el servidor
2. El contador debe aparecer en amarillo `~0 (log)` si A2S no responde
3. Al conectarse un jugador, debe subir a `~1 (log)`
